# 第八轮：前置图片入口、精确 RGB 候选与身份保护

日期：2026-10-09。版本：0.1.20；冻结对照为本轮改动前构建的工作区 0.1.19 worker，SHA-256 `1805b29a2dafaf13b5733833d783975c6b0c82a2b7eee4318e559cbac74c2b5d`。落实 [0.1.19 审核计划](PDF-OPTIMIZATION-AUDIT-0.1.19.md) 的步骤 0 / 1 / 2；大图分行处理、扩大精确共享、桌面超采样、CMYK JPEG 和自动字体子集仍是后续工作。

## 已实现

1. **统一对象身份保护。** 内容流合并、旧流去重、图片共享和资源图共享使用共同的保守身份扫描。标签、MCR / Stm、OBJR、独立批注外观及表单等身份绑定文档不再合并流对象；仍允许不涉及流的纯资源字典共享，例如标准字体字典。扫描超预算或过深时保护流。独立反例复现了冻结版把两个同 MCID / 不同 Stm 的流，以及两个独立 AP 外观，各合并成一个的问题；新版在四个保留档位均保留两个身份，字段名称和值不变。它们的体积比较与正常压缩收益分开记录。
2. **前置并有界地规范化图片表示。** 在资源清理 / 图片共享 / 图片优化前，解析受支持的 Filter 与 DecodeParms 数组、null、间接引用，解引用图片尺寸、位深和颜色空间的受支持表示。包装 JPEG / G4 保留终端压缩字节和有效非默认参数；LZW / RunLength 严格解码后改用 Flate，保留预测器行的原始中间字节及其参数。LZW EarlyChange 0 / 1、PNG 行预测、TIFF 8 / 16 位及 1 / 2 / 4 位打包样本分别验证。外部流、未知参数、损坏数据与超预算工作跳过，不删除未知参数来强行解锁像素重编码。
3. **补充超过 256 色的精确 RGB Flate 候选。** 在分散行和两侧区域做轻量压缩探测，值得尝试时生成 Sub、Up、五种行预测自适应的完整候选；与原编码、既有精确 Indexed / G4 / Flate 和 MozJPEG 比较实际字典加负载成本。抽样只决定是否工作，不改像素、不作为全图等价证明。胜出的 RGB 候选须完整解码回相同输入样本，并保存输入缓冲区的尺寸、字节数与 SHA-256，供独立 PDF 解码校验。噪声负例、预算与取消有专门测试。
4. **两个模式都比较完整文件。** 保留模式从本次固定来源生成旧方案与前置规范化 / RGB 方案；不会对已经有损量化的结果再量化，JPEG 缓存跨两个方案复用。整页模式只渲染一次，从同一份页面像素生成旧编码与新增精确编码；有改善的页面替换组成独立完整文件。候选严格重读 / 引用核对成功并且更小时才替代现有完整方案。保留模式继续只导出比输入更小的结果；图片模式仍按用户选择导出每页单图。
5. **补齐最终诊断。** `images` 是所选处理路径的尝试记录，保留源身份及原字节数；`output_images` 从胜出的实际序列化 PDF 重新读取最终对象编号、编码过滤器、尺寸和字节数。`image_optimization` 记录两个完整文件的选择，`image_preparation` / `rgb_flate` 记录工作、跳过、预算及固定样本证明。未导出时，`size_after` 和 `output_images` 指向实际保留的原件，不再冒充候选结果。

JPEG 的精确压缩与 RGB 样本精确压缩分别处理。严格无损不会把 JPEG 解码器的取整结果固化成 Flate；JPEG 系数、量化表、采样与标记保留。新增规范化方案在严格无损 / 保真 JPEG 系数候选中保留源的顺序 / 渐进扫描方式：本轮曾发现改变扫描方式虽然系数相同，CoreGraphics 会有小幅像素差异，现已收紧并保留反例。保真仍保持原图尺寸及既有 JPEG 参数；它不代表整个 PDF 严格无损。

本轮不改变 JPEG 默认质量、DPI、既有矢量精度参数或渲染 / 重采样算法。CLI 沿用预算内的 2 倍渲染后 Lanczos3 缩小，桌面沿用生产 PDF.js / 原生 Canvas 的 1 倍路径；两条渲染链分别验收。

## 预算与性能边界

- 额外完整方案最多 50,000 对象、约 64 MiB 的流及字典 / 字符串负载；按操作数和深度限制资格检查，包含 trailer 数据。资格限制不会成为默认输入文件大小上限。
- 图片规范化每层最多 4 MiB、每文档工作量 16 MiB、四秒软限额；受调用方限制约束。支持表示不等于无限大图片也会进入新增通路。
- RGB 新增工作每个输入样本最多 8 MiB、文档三次完整预测的总工作量 32 MiB、最多八次完整尝试，累计新增时间四秒及阶段墙钟十二秒软限额。边界处检查取消；它们不是单次 FFI 调用的硬中断。旧编码路径继续可用，跳过在报告中显示。
- JPEG 缓存沿用每文档 32 MiB / 256 项上限；超过缓存预算可能再次计算同一来源的编码，不会反复量化上一次的编码结果。原图片诊断使用哈希表匹配，避免大量图片时逐项线性查找。
- `/usr/bin/time -l` 的一次独立小样本测量：原生 RGB / 保真 25 → 34 ms，峰值 RSS 11.0 → 11.7 MiB；噪声 / 均衡 56 → 58 ms、约 12 MiB；100 页共享图 / 保真 39 → 69 ms，RSS 13.6 → 15.9 MiB。这不是大图峰值上限或普遍速度结论，也不是桌面渲染耗时；原记录在 `tmp/round8-images/profile/`。

## 桌面生产渲染验证

原生 WKWebView 执行实际 `src/rasterCompress.ts` 与本地 PDF.js / 原生 Canvas，Tauri IPC 适配为本机 QA 服务。Rust 生产计划和同一套 RGB 暂存协议分别交给冻结 / 新版 worker。既有六类加原生相关 RGB、10 页文档，三个档位共 **24 例、51 页**：5 例变小、19 例完整字节相同，没有体积退步；变化页面由独立 pypdf 解码核对与实际暂存 RGB 全部相同，其余页面编码不变。

例如包装 PNG 预测图 / 均衡从 137,566 B 到 10,028 B，相关 RGB / 均衡从 27,680 B 到 18,613 B，10 页 / 均衡从 289,767 B 到 272,682 B。它们是这条桌面生产渲染链的结果，不以 CLI 数据代替。仍使用隔离 WKWebView 进程、离屏调度适配及 QA IPC；未宣称真实界面连续任务、原生 Tauri IPC 或 Windows WebView2 已完成验收。

## 独立正确性与交付验证

- 396 个新结果的所有 **1,152 页**通过 PDF.js 200 DPI 检查，无解码警告；保留模式文字及位置与原件一致，530 个页面 / 档位组合的像素也与源完全相同。严格无损逐页源像素必须相同，保真沿用原分辨率和既有有损参数，不将两种承诺混为一谈。

- 16 次独立身份反例校验验证 MCR 指向原 Contents 数组中的正确项，独立字段 / AP 身份和字段名称 / 值保留。另有 100 页端到端 Rust 回归，逐页尺寸、旋转、裁剪和 UserUnit，以及最终 `output_images` 的对象 / 字节 / 尺寸校验。

画质验收明确区分源 PDF 渲染、固定页面输入像素和输出编码。严格无损要求各阅读器与源像素相同；保真新结果对源的 RMSE 不高于冻结版。均衡 / 更小新解锁的包装图片会按用户选定的既有有损参数处理：10 个页面 / 档位组合从旧版未处理、与源相同，变为有损结果，这是实际策略生效，不能称为画质无损。
